## The problem

A research turn in an agent product is slow by nature. The model reads the request, calls a search tool, reads the results, maybe calls two more tools, and then writes several paragraphs. Tens of seconds is normal. Nobody will watch a spinner for that long, so the answer has to stream: text appears as it is written, tool calls show up as progress, and a shortlist of products lands at the end.

Streaming from a model to one server is a solved problem. Streaming through **three** services is where it gets interesting:

Each hop has a different job, and each one broke in a different way.

## Hop 1: the browser cannot use EventSource

The obvious tool for server-sent events in a browser is `EventSource`. It is the wrong tool here. It only issues GET requests, cannot send a body, and cannot set headers. A research request carries a JSON body with the message, session and buyer context.

So the browser POSTs with `fetch` and reads the response body as a stream:

```ts title="stream.ts" {9-11}
export async function* readEvents(res: Response): AsyncGenerator<{ event: string; data: string }> {
  const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader()
  let buffer = ""
  for (;;) {
    const { value, done } = await reader.read()
    if (done) return
    buffer += value
    // A network chunk can end mid-event. Only complete frames, ended by a blank line, are parsed;
    // the remainder waits for the next chunk.
    const frames = buffer.split("\n\n")
    buffer = frames.pop() ?? ""
    for (const frame of frames) {
      const event = /^event: (.*)$/m.exec(frame)?.[1] ?? "message"
      const data = frame
        .split("\n")
        .filter((l) => l.startsWith("data: "))
        .map((l) => l.slice(6))
        .join("\n")
      yield { event, data }
    }
  }
}
```

The highlighted lines are the whole trick. TCP does not respect your message boundaries, so a frame can arrive in two chunks, and parsing every chunk as if it were complete produces corrupted JSON roughly once in a few hundred turns. That is rare enough to pass every demo and common enough to annoy real users.

Parsed events go into a pure reducer that turns them into UI state. Because it is a pure function of events, every edge case, including duplicate and out-of-order events, can be unit-tested without a server.

## Hop 2: the backend-for-frontend must not buffer

The browser never holds a token for the API. It calls a Next.js route, which reads the session from an HttpOnly cookie, attaches the bearer token server-side, and forwards the request. For a stream, the proxy must hand back the upstream body as-is rather than awaiting it:

```ts title="app/api/proxy/[...path]/route.ts"
const upstream = await fetch(target, { method: "POST", headers, body: req.body, duplex: "half" })
return new Response(upstream.body, {
  status: upstream.status,
  headers: { "content-type": "text/event-stream", "cache-control": "no-cache", "x-accel-buffering": "no" },
})
```

<Callout type="warning" title="Any proxy can buffer">
  Returning `await upstream.text()` here, or a reverse proxy in front of it with buffering on, silently turns the stream into one long response. The `X-Accel-Buffering: no` header tells nginx-style proxies to pass bytes through. Test streaming through the real ingress, not just against localhost.
</Callout>

## Hop 3: the gateway cannot be a byte pipe

The tempting design for the gateway is to pipe bytes from the agent service to the browser. It doesn't survive contact with real requirements:

- **Persistence.** Every turn has to be saved: the user's message, the assistant's reply, and the recommended products. Someone has to own that, and the gateway already owns the database.
- **Partial replies.** If the agent stream dies at second 25 of 30, the user should keep the 25 seconds of answer they already saw.
- **Duplicates.** Some agent builds emitted the completion event twice. A byte pipe passes the duplicate through and the UI finalises the turn twice.

So the gateway parses the agent's events, writes state as it goes, and re-emits its own events. The shape of the work:

<Steps>
  <Step title="Before calling the agent">
    Check the user owns the session. Save the user message and an empty assistant reply marked as streaming. Emit a session event so the UI has ids to work with.
  </Step>
  <Step title="While streaming">
    Accumulate text deltas, forward each event, and remember tool calls and the latest shortlist.
  </Step>
  <Step title="On the first completion event">
    Save the final reply and shortlist, mark the turn complete, and forward it. Drop any later completion event for the same turn.
  </Step>
  <Step title="On a broken stream">
    Save what arrived, mark the turn as partial, and emit an error event the UI can show next to the text the user already has.
  </Step>
</Steps>

## Three timeouts, not one

The gateway calls the agent with an HTTP client, and the client's timeout turned out to be three separate questions:

| Timeout | Value | What it protects against |
| --- | --- | --- |
| Connect | ~10 s | An unreachable agent. Fail fast and tell the user. |
| Read | ~180 s | A cold start plus the first model token, then the gaps between tool calls. Too short and healthy turns die. |
| Pool | ~20 s | A saturated connection pool. Without a limit, requests queue silently and the user waits on nothing. |

A single "timeout = 30" either kills slow-but-healthy turns or lets a dead agent hang the user for minutes. Most HTTP clients let you set these separately; few examples show it.

## The platform: CPU between chunks

The last stall had nothing to do with code. Serverless containers commonly throttle CPU outside of request handling. A streaming response is a single long request, but the work between chunks, such as parsing the model's output and running tool calls, still needs CPU. With throttling on, streams stalled mid-turn under load.

Two settings fixed it: keep CPU allocated at all times on the agent service, and keep at least one instance warm so a turn never starts with a cold boot. Both cost money, and both are cheaper than users abandoning a stalled answer.

## What I'd add next

- **An idempotency key per turn.** A retried POST should resume or replay a turn, not pay for a second one.
- **One trace id across all three hops.** Debugging a stall means following a single turn through every service's logs; that needs the same id at every hop.
- **A test that streams through the real ingress.** The buffering bugs only appear with the real proxies in the path.

<Takeaways>
- Use fetch and a reader for POSTed streams, and only ever parse complete frames.
- Make the service that owns persistence a stateful proxy, and let it absorb duplicates and partial failures.
- Split connect, read and pool timeouts; each answers a different question.
- On serverless platforms, check CPU allocation before you blame your code for a stall.
</Takeaways>
